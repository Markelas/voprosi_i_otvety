# Виды рендеринга (SSG, ISR, SSR, CSR)

## Краткий ответ для собеседования

**CSR** (Client-Side Rendering) — рендеринг на клиенте (браузере), быстрая навигация, но медленная первая загрузка и плохое SEO. **SSR** (Server-Side Rendering) — рендеринг на сервере для каждого запроса, быстрая первая загрузка, хорошее SEO, но нагрузка на сервер. **SSG** (Static Site Generation) — генерация HTML на этапе сборки, моментальная загрузка, но данные статичны. **ISR** (Incremental Static Regeneration) — статика + регенерация по требованию или по времени, баланс между SSG и SSR. **Гидрация** — «оживление» уже отрисованного HTML на клиенте: React подключает обработчики событий к существующим узлам DOM. **RSC** (React Server Components) — компоненты, выполняющиеся только на сервере; их код не попадает в клиентский бандл, клиент получает готовый результат.

**В Next.js App Router компоненты по умолчанию являются Server Components. Они выполняются в серверном окружении и позволяют, например, <u>получать данные напрямую с сервера и не отправлять соответствующий код в клиентский bundle</u>.
Client Components обозначаются `'use client'` и используются для интерактивности, состояния и browser API. <u>Они входят в клиентский bundle и гидратируются в браузере.</u>**

<u>**Server Component может импортировать Client Component, но Client Component не может напрямую импортировать Server Component</u>. Если нужно вложить серверный компонент внутрь клиентского, его обычно передают через `children` или другой prop из Server Component. Тогда серверный компонент продолжает обрабатываться на сервере, а Client Component получает его как часть React-дерева.**

## Самое важное: где рендерится и что получает клиент

На собеседовании часто путают **когда** страница строится и **что** приходит в браузер. Ниже — схема «по слоям».

### Что вообще может прийти клиенту

| Артефакт | Что это | Зачем |
|----------|---------|--------|
| **HTML** | Готовая разметка страницы | Сразу показать контент (FCP), SEO |
| **JS-бандл / чанки** | Код React-приложения | Интерактивность, навигация, повторный рендер |
| **CSS** | Стили | Оформление |
| **Данные / JSON** | Props, state, API-ответ | Чтобы клиент знал, с каким состоянием работать |
| **RSC payload** | Специальный поток результата Server Components | Встроить серверный результат без кода этих компонентов |

Не всегда приходит всё сразу. Зависит от вида рендеринга.

---

### Сводная схема: когда и где рендерится

| Вид | Когда строится HTML | Где строится HTML | Что делает клиент | Что приходит клиенту на первый заход |
|-----|---------------------|------------------|-------------------|--------------------------------------|
| **CSR** | После загрузки JS | **Только в браузере** | Сам рендерит UI в DOM | Почти пустой HTML + JS (+ CSS) |
| **SSR** | На **каждый** запрос | **На сервере**, потом гидрация на клиенте | Гидрация + дальше SPA | **Готовый HTML** + JS + данные для гидрации |
| **SSG** | Один раз на **build** | На сервере/CI при сборке | Гидрация + дальше SPA | **Готовый HTML** (часто с CDN) + JS |
| **ISR** | На build + потом **перегенерация** | Сервер/платформа в фоне | Как у SSG | Как у SSG: готовый HTML + JS |

Ключевая мысль:

- **CSR** — HTML почти не «готов» на сервере, браузер **строит** страницу из JS.
- **SSR / SSG / ISR** — браузер **сначала получает HTML**, а JS потом его «оживляет» (гидрация).

---

### Одна картинка для запоминания

```text
CSR:
  Запрос → сервер отдаёт оболочку + JS
         → браузер выполняет JS
         → React строит DOM
         → пользователь видит страницу

SSR:
  Запрос → сервер рендерит React в HTML
         → клиент получает HTML (+ JS)
         → пользователь уже видит контент
         → JS делает гидрацию
         → страница становится интерактивной

SSG:
  Build  → сервер заранее делает HTML-файлы
  Запрос → CDN/сервер отдаёт готовый HTML (+ JS)
         → гидрация на клиенте

ISR:
  Как SSG, но HTML может тихо пересобраться позже
  (по таймеру или on-demand)
```

## CSR — Client-Side Rendering

### Что это

**Рендеринг на стороне клиента** — браузер получает почти пустой HTML + JavaScript, затем JavaScript строит DOM и рендерит страницу.

### Где и когда рендерится

| Этап | Где | Что происходит |
|------|-----|----------------|
| Ответ сервера | Сервер / CDN | Отдаёт оболочку HTML и ссылки на JS/CSS |
| Построение UI | **Только клиент** | React выполняет `createRoot(...).render(...)` и строит дерево |
| Навигация внутри SPA | Клиент | Новые экраны тоже рендерятся в браузере, без полного HTML с сервера |

**Важно:** в чистом CSR **нет серверного React-рендера** страницы. Сервер — просто раздатчик статики (HTML-оболочка + бандлы).

### Что приходит клиенту

На первый заход обычно:

1. **Минимальный HTML** — оболочка, часто с `<div id="root"></div>`
2. **JS-чанки** — runtime, vendor, app-бандл, иногда code-split куски
3. **CSS**
4. Потом уже **данные с API** (отдельными запросами)

Типичный HTML:

```html
<!DOCTYPE html>
<html>
  <head>
    <link rel="stylesheet" href="/assets/index.css" />
  </head>
  <body>
    <div id="root"></div>
    <script type="module" src="/assets/index.js"></script>
  </body>
</html>
```

Что **не** приходит готовым:

- полноценная HTML-разметка контента страницы
- SEO-значимый текст внутри body (его ещё нет, пока JS не отработал)

### Как работает пошагово

1. Сервер/CDN отдаёт оболочку HTML + ссылки на JS/CSS
2. Браузер парсит HTML → видит пустой `#root`
3. Браузер качает и выполняет JS-чанки
4. React монтируется и **рендерит** дерево компонентов в DOM
5. Часто после этого идут `fetch` за данными → ещё один рендер
6. Пользователь наконец видит полноценный UI

### Метрики и ощущения

- **TTFB** часто хороший (отдать статику легко)
- **FCP / LCP** хуже: нужно дождаться JS + рендера (+ данных)
- **TTI** ещё позже: пока JS не готов, интерактива нет

### Преимущества

- **Быстрая навигация** — после загрузки JS переходы мгновенные (SPA)
- **Интерактивность** — всё на клиенте, богатый UX
- **Простая инфраструктура** — не нужен сервер рендеринга, статика на CDN

### Недостатки

- **Медленная первая загрузка (FCP)** — нужно загрузить и выполнить JS
- **Плохое SEO** — поисковики сначала видят пустой HTML
- **Проблемы на слабых устройствах** — тяжёлый JS долго выполняется
- **Waterfall:** HTML → JS → API → UI

### Когда использовать

- **SPA** — админки, дашборды, личные кабинеты
- **SEO не важен** — внутренние инструменты, приложения за авторизацией
- **Много интерактивности** — сложные интерфейсы, реал-тайм

**Примеры:** CRA, Vite SPA, многие React-админки.

## SSR — Server-Side Rendering

### Что это

**Рендеринг на стороне сервера** — сервер на **каждый запрос** рендерит React в HTML и отдаёт готовую страницу. Потом клиентский JS делает гидрацию.

### Где и когда рендерится

| Этап | Где | Что происходит |
|------|-----|----------------|
| Первый HTML | **Сервер, на каждый request** | `renderToString` / `renderToPipeableStream` |
| Показ контента | Клиент | Браузер сразу рисует полученный HTML |
| Интерактивность | Клиент | Гидрация: React «подцепляется» к DOM |
| Дальнейшая навигация | Обычно клиент | Как SPA (CSR), без полного SSR на каждый клик |

**Важно для собеседования:**  
SSR делает серверный рендер **для первого ответа** (document request). Дальше Next.js/Remix часто работают как SPA: клиентский роутинг + догрузка данных/чанков.

### Что приходит клиенту

На первый заход:

1. **Полноценный HTML** уже с контентом страницы
2. **JS-бандлы / чанки** для гидрации и дальнейшей работы
3. **CSS**
4. Часто **сериализованные данные** (например, `__NEXT_DATA__` в Pages Router) — чтобы клиент гидрировался с теми же props, что были на сервере

Упрощённо:

```html
<!DOCTYPE html>
<html>
  <body>
    <!-- Уже готовый контент -->
    <div id="root">
      <h1>Товар iPhone</h1>
      <button>Купить</button>
    </div>

    <!-- Данные для гидрации -->
    <script id="__NEXT_DATA__" type="application/json">
      {"props":{"pageProps":{"title":"Товар iPhone"}}}
    </script>

    <!-- JS, который оживит страницу -->
    <script src="/_next/static/chunks/main.js"></script>
    <script src="/_next/static/chunks/page.js"></script>
  </body>
</html>
```

Что важно понять:

- HTML уже есть → пользователь **видит** контент до выполнения всего JS
- JS всё равно нужен → без него нет полноценной интерактивности React
- данные для гидрации нужны, чтобы серверный и клиентский первый рендер совпали

### Как работает пошагово

1. Пользователь запрашивает `/product/1`
2. Сервер достаёт данные (БД/API)
3. Сервер рендерит React → HTML-строка/поток
4. Браузер получает HTML и **сразу показывает** контент (FCP)
5. Браузер параллельно/следом качает JS-чанки
6. React делает **гидрацию**
7. Страница становится интерактивной (TTI)
8. Дальше пользователь кликает по приложению → часто уже CSR-навигация

### Преимущества

- **Быстрая первая загрузка (FCP)** — контент в HTML сразу
- **Хорошее SEO** — поисковик видит готовый HTML
- **Работает без JS на уровне контента** — текст/разметка уже есть
- **Актуальные данные** — рендер на запрос

### Недостатки

- **Нагрузка на сервер** — рендер на каждый request
- **Выше TTFB** — сервер должен успеть сходить за данными и отрендерить
- Нужна инфраструктура Node-сервера / edge runtime
- Риск hydration mismatch, если сервер и клиент отрендерят по-разному

### Когда использовать

- Динамический контент (новости, профили, корзина)
- SEO важен
- Персонализация (user, cookies, geo)

**Примеры:** Next.js `getServerSideProps`, Remix loaders, кастомный SSR.

## SSG — Static Site Generation

### Что это

**Генерация статических страниц** — HTML создаётся **на этапе сборки** (`build`), потом отдаётся как статический файл (часто с CDN).

### Где и когда рендерится

| Этап | Где | Что происходит |
|------|-----|----------------|
| Build time | CI / сервер сборки | React рендерит страницы в HTML-файлы |
| Request time | CDN / static hosting | Просто отдаёт уже готовый файл |
| После загрузки | Клиент | Гидрация JS, дальше SPA-поведение |

**Важно:** в момент запроса пользователя **рендера React на сервере обычно нет**. Сервер/CDN только раздаёт заранее собранный HTML.

### Что приходит клиенту

Похоже на SSR по форме ответа:

1. **Готовый HTML** страницы
2. **JS-чанки** для гидрации
3. **CSS**
4. Часто вшитые/связанные **статические данные** страницы

Отличие от SSR не в «что пришло», а в **когда это HTML было построено**:

- SSR: HTML родился **сейчас**, на этот запрос
- SSG: HTML родился **раньше**, на build

### Как работает пошагово

1. На `build` фреймворк знает список страниц
2. Для каждой страницы достаёт данные и рендерит HTML
3. Артефакты кладутся на CDN/хостинг
4. Пользователь запрашивает URL → мгновенно получает готовый HTML
5. JS гидрирует страницу

### Преимущества

- **Моментальная загрузка** — HTML уже готов, CDN близко
- **Отличное SEO**
- **Отличная масштабируемость** — почти нет compute на запрос
- **Безопаснее** — меньше живой серверной поверхности

### Недостатки

- Данные могут устареть до следующего билда
- Долгий build на очень большом числе страниц
- Плохо для персонализации «на лету»

### Когда использовать

- Документация, лендинги, блоги, маркетинг
- Контент меняется редко
- Нужна максимальная скорость

**Примеры:** Next.js `getStaticProps`, Gatsby, Astro (в static-режиме).

## ISR — Incremental Static Regeneration

### Что это

**Инкрементальная статическая регенерация** — как SSG, но страницу можно **пересобрать позже** без полного ребилда всего сайта: по таймеру (`revalidate`) или on-demand.

### Где и когда рендерится

| Этап | Где | Что происходит |
|------|-----|----------------|
| Первый build | CI | Страницы генерируются как в SSG |
| Обычный запрос | CDN/кэш | Отдаётся уже сохранённый HTML |
| Когда страница «протухла» | Сервер/платформа **в фоне** | Регенерируется новый HTML |
| Клиент | Браузер | Как обычно: HTML + гидрация |

Типичная модель **stale-while-revalidate**:

1. Пользователь получает **текущую** (возможно слегка старую) версию HTML — быстро
2. В фоне стартует регенерация
3. Следующие пользователи уже получают обновлённую версию

### Что приходит клиенту

С точки зрения браузера почти всегда как у SSG:

- **готовый HTML**
- **JS для гидрации**
- CSS / данные страницы

Клиент обычно **не знает**, что страница когда-то была пересобрана в фоне. Для него это просто быстрый HTML-ответ.

### Как работает (идея Next.js)

```js
export async function getStaticProps() {
  const data = await fetch('...');
  return {
    props: { data },
    revalidate: 60 // страница может обновляться раз в ~60 секунд
  };
}
```

Процесс:

1. Есть закэшированная статическая версия
2. Пришёл запрос после истечения `revalidate`
3. Сразу отдаём старую версию
4. В фоне строим новую
5. Кэш обновляется

Есть и **on-demand ISR**: регенерация по событию (CMS webhook, `revalidatePath`, `revalidateTag`).

### Преимущества

- Скорость почти как у SSG
- Данные свежее, чем у чистого SSG
- Не надо пересобирать весь сайт из-за одной страницы
- Нагрузка ниже, чем у SSR на каждый запрос

### Недостатки

- Возможна краткая отдача stale-данных
- Сложнее ментальная модель кэша и инвалидации
- Нужна платформа, которая умеет регенерацию

### Когда использовать

- Каталоги, карточки товаров, контент из CMS
- Нужны и скорость, и периодические обновления
- Большие сайты с тысячами URL

**Примеры:** Next.js `revalidate`, on-demand revalidation.

## Что именно происходит на клиенте после прихода ответа

Это частый уточняющий вопрос.

### CSR

```text
HTML-оболочка
   → загрузка JS-чанков
   → React render в пустой root
   → (часто) fetch данных
   → повторный render
   → интерактивность
```

Гидрации в классическом смысле **нет**, потому что нечего «оживлять»: DOM ещё не был построен сервером.

### SSR / SSG / ISR

```text
Готовый HTML уже на экране
   → загрузка JS-чанков
   → hydration
   → обработчики/state подключены
   → дальше клиентский роутинг как SPA
```

То есть:

- **первый paint** даёт HTML
- **интерактивность** даёт JS
- после гидрации приложение ведёт себя как CSR

## HTML vs JS: что за что отвечает

| Задача | CSR | SSR/SSG/ISR |
|--------|-----|-------------|
| Показать текст/контент впервые | JS должен сначала отрендерить | Уже есть в HTML |
| SEO-контент в первом ответе | Слабо / нет | Есть |
| Клики, формы, клиентский state | JS | JS после гидрации |
| Переход на другую страницу без reload | JS | Обычно тоже JS (SPA-навигация) |
| Персональные данные на первый ответ | Через API после mount | Удобнее через SSR |

Коротко:

- **HTML** отвечает за «увидеть»
- **JS** отвечает за «взаимодействовать»
- в CSR HTML почти не помогает «увидеть контент»
- в SSR/SSG/ISR HTML как раз и даёт быстрый первый экран

## Гидрация (Hydration)

### Что это

**Гидрация** — процесс, когда React на клиенте подключается к уже отрисованному HTML и делает его интерактивным: навешивает обработчики, восстанавливает дерево компонентов, подключает state/effects.

Простыми словами: сервер/build отдал «мёртвый», но правильный HTML → браузер его показал → JS React «оживил» те же DOM-узлы.

### Когда нужна

- SSR
- SSG
- ISR

В чистом CSR гидрации нет: там сразу клиентский mount/render.

### Зачем нужна

Без гидрации после SSR/SSG был бы статичный документ. С гидрацией получаем лучшее из двух миров:

1. быстрый первый HTML
2. дальше поведение SPA

### Что делает React при гидрации

- сопоставляет виртуальное дерево с существующим DOM
- не пересоздаёт всю разметку с нуля
- вешает listeners
- если HTML клиента не совпал с серверным → **hydration mismatch**

### Главное правило гидрации

**Первый рендер на клиенте должен дать ту же разметку, что уже пришла с сервера.**

Если сервер нарисовал одно, а клиент при первом рендере рисует другое — React ругается.

## Ошибки гидрации (Hydration Mismatch)

### Что это

**Hydration mismatch** — ситуация, когда DOM, который React ожидает на клиенте, **не совпадает** с HTML, который уже был отрендерен на сервере.

В консоли обычно что-то вроде:

```text
Warning: Text content does not match server-rendered HTML.
Hydration failed because the initial UI does not match what was rendered on the server.
```

### Почему это плохо

- React может перерисовать кусок дерева заново
- возможны мигания UI
- хуже производительность
- иногда ломается интерактивность
- в React 18+/Next.js это частая причина странных багов на первом экране

---

### Когда возникают ошибки гидрации

#### 1. Недетерминированные значения: `Date.now()`, `new Date()`, `Math.random()`

Классический пример для собеседования.

```tsx
function Clock() {
  return <div>{Date.now()}</div>;
}
```

Что происходит:

1. Сервер рендерит время `T1`
2. HTML уходит клиенту с `T1`
3. Клиент при гидрации вызывает `Date.now()` снова → уже `T2`
4. Разметка не совпала → mismatch

То же самое с:

- `new Date().toLocaleString()`
- `Math.random()`
- `crypto.randomUUID()` на первом рендере

**Как правильно:**

- не рендерить такие значения сразу в SSR/SSG HTML
- считать их на клиенте после монтирования (`useEffect` / `useState` + mount flag)
- или брать одно и то же значение с сервера и прокидывать как данные

#### 2. Браузерные API на первом рендере

На сервере нет `window`, `document`, `localStorage`.

Плохо:

```tsx
function Theme() {
  const theme = localStorage.getItem('theme'); // на сервере упадёт или даст другое
  return <div>{theme}</div>;
}
```

Типичные источники:

- `window.innerWidth`
- `navigator.language`
- `localStorage` / `sessionStorage`
- проверка `typeof window !== 'undefined'` с разным UI сразу в render

**Как правильно:**

- первый рендер делать одинаковым на сервере и клиенте
- browser-only логику включать после mount

#### 3. Невалидный HTML / неправильная вложенность тегов

Браузер сам «чинит» HTML до того, как React начнёт гидрацию.

Примеры:

- `<p>` внутри `<p>`
- `<div>` внутри `<p>`
- `<tr>` без `<table>` / неправильная структура таблиц
- интерактивный элемент не там, где React ожидал

Сервер отдал одну структуру → браузер переписал DOM → React видит другое.

#### 4. Разный контент из-за locale / timezone / formatting

На сервере и клиенте могут отличаться:

- часовой пояс
- язык
- формат чисел и дат

Пример:

```tsx
new Date(date).toLocaleDateString()
```

На сервере в UTC/`en-US`, у пользователя в `ru-RU` и другом timezone → другая строка.

#### 5. Условный рендер по user-agent / device

```tsx
if (isMobile) return <MobileNav />;
return <DesktopNav />;
```

Если `isMobile` на сервере посчитали иначе, чем на клиенте, будет mismatch.

#### 6. Расширения браузера и внешние скрипты

Иногда HTML меняют:

- переводчики страниц
- password managers
- adblock / grammarly-подобные расширения

Они вставляют свои атрибуты/узлы в DOM → React видит «лишнее».

Это не всегда баг приложения, но на собеседовании полезно упомянуть.

#### 7. Несовпадение данных props / кэша

Сервер отрендерил с одними данными, а клиент при гидрации получил другие:

- разные env
- разные API-ответы
- гонка кэша
- на клиенте пересчитали данные иначе

#### 8. `suppressHydrationWarning` как костыль

Иногда для заведомо разных кусков используют:

```tsx
<time suppressHydrationWarning>{new Date().toLocaleString()}</time>
```

Это не «лечение причины», а подавление warning для конкретных узлов, где расхождение ожидаемо.

### Как думать о проблеме на собеседовании

Хорошая формулировка:

> Ошибка гидрации возникает, когда первый клиентский рендер даёт другую разметку, чем HTML с сервера. Самые частые причины — `Date.now()`, `Math.random()`, `localStorage`, locale/timezone и невалидный HTML.

### Как избегать

1. Первый рендер должен быть **детерминированным**
2. Всё, что зависит от браузера/времени/рандома — после mount
3. Одинаковые данные на сервере и клиенте для гидрации
4. Валидная HTML-структура
5. Для заведомо клиентского UI — Client Component + отложенный рендер
6. В крайних случаях — `suppressHydrationWarning` точечно

### Мини-схема

```text
Сервер: render → HTML_A
Клиент: первый render → HTML_B

HTML_A === HTML_B  → гидрация ок
HTML_A !== HTML_B  → hydration mismatch
```

### Кратко про гидрацию и её ошибки

Гидрация = «оживление» готового HTML клиентским React.  
Ошибка гидрации = сервер и клиент нарисовали разное.  
Самый популярный пример — `Date.now()` / `new Date()` / `Math.random()` / `localStorage` на первом рендере.

## RSC — React Server Components

### Что это

**React Server Components (RSC)** — компоненты, которые выполняются **только на сервере**. Их исходный код **не попадает** в клиентский JS-бандл. Клиент получает уже результат их работы.

### Чем RSC отличается от классического SSR

| | Классический SSR | RSC |
|--|------------------|-----|
| Что рендерит сервер | Обычно HTML страницы | Server Components → специальный payload + HTML/stream |
| Есть ли код этих компонентов у клиента | Да, для гидрации почти всего дерева | Кода Server Components на клиенте нет |
| Гидрация | Часто почти всего UI | В основном Client Components / «острова» |
| Бандл | Толще | Обычно тоньше |

Важная формулировка для собеседования:

- **SSR** — «сервер нарисовал HTML, но клиент всё равно скачает JS этих компонентов для гидрации»
- **RSC** — «часть компонентов вообще живёт только на сервере, клиент получает результат, а не их код»

### Что приходит клиенту при RSC-модели (упрощённо)

- HTML и/или **RSC payload** (поток описания UI)
- JS только для Client Components
- меньше JS, чем если бы всё было клиентским

### Плюсы RSC

- меньший клиентский бандл
- прямой доступ к БД/секретам на сервере
- лучше security boundary
- удобный гибрид: серверные куски + клиентские острова

### Ограничения

- нельзя `useState` / `useEffect` / DOM-события в Server Components
- нужна поддержка фреймворка (Next.js App Router и т.п.)
- надо явно проектировать границу server/client

## Сравнение

| Параметр | CSR | SSR | SSG | ISR |
|----------|-----|-----|-----|-----|
| **Когда строится HTML** | В браузере после JS | На каждый запрос | На build | На build + позже в фоне |
| **Где строится HTML** | Клиент | Сервер | CI/сервер сборки | CI + сервер регенерации |
| **Что в первом ответе** | Оболочка + JS | Полный HTML + JS | Полный HTML + JS | Полный HTML + JS |
| **Гидрация** | Нет | Да | Да | Да |
| **FCP** | Медленнее | Быстро | Очень быстро | Очень быстро |
| **SEO** | Плохое | Отличное | Отличное | Отличное |
| **Свежесть данных** | Актуальные | Актуальные | На момент build | Почти актуальные |
| **Нагрузка на сервер** | Нет / минимальная | Высокая | Нет | Низкая |
| **Масштабируемость** | Отлично | Средне | Отлично | Отлично |
| **Использование** | SPA, админки | Динамика + SEO | Статика | Полудинамика |

## Как выбирать на собеседовании

```text
SEO не нужен, всё за авторизацией?
  → CSR

Нужен SEO + данные разные у каждого пользователя / очень свежие?
  → SSR

Нужен SEO + контент почти не меняется?
  → SSG

Нужен SEO + контент меняется, но не обязательно в ту же миллисекунду?
  → ISR
```

Ещё один сильный ответ:

- **CSR** оптимизирует разработку интерактивных приложений
- **SSR** оптимизирует первый ответ с актуальными данными
- **SSG** оптимизирует скорость и стоимость раздачи
- **ISR** ищет компромисс между SSG и SSR

## Вопросы на собеседовании

| Вопрос | Краткий ответ |
|--------|----------------|
| Что такое CSR? | Рендеринг на клиенте: приходит оболочка + JS, React сам строит DOM |
| Что приходит клиенту при CSR? | Почти пустой HTML, JS-чанки, CSS; контент появляется после выполнения JS |
| Что такое SSR? | На каждый запрос сервер рендерит HTML, потом клиент гидрирует |
| Что приходит клиенту при SSR? | Готовый HTML + JS (+ данные для гидрации) |
| Что такое SSG? | HTML генерируется на build и потом просто раздаётся |
| В чём разница SSR и SSG? | SSR строит HTML на запрос, SSG — заранее на сборке; клиенту в обоих случаях приходит HTML |
| Что такое ISR? | SSG + фоновая/on-demand перегенерация страниц |
| Когда рендерится ISR? | Сначала как статика; устаревшие страницы пересобираются в фоне |
| Есть ли гидрация в CSR? | Нет, там обычный client render/mount |
| Когда нужна гидрация? | После SSR/SSG/ISR, когда HTML уже есть |
| Почему после SSR всё равно нужен JS? | HTML даёт контент, JS даёт интерактивность и SPA-навигацию |
| Что такое ошибка гидрации? | Серверный HTML и первый клиентский рендер не совпали |
| Из-за чего бывает hydration mismatch? | `Date.now()`, `Math.random()`, `localStorage`, locale/timezone, невалидный HTML, разный UI для mobile/desktop |
| Как избежать ошибок гидрации? | Первый рендер делать одинаковым; browser-only/рандом/время — после mount |
| Что такое RSC? | Компоненты только для сервера; их код не едет в клиентский бандл |
| Чем RSC отличается от SSR? | SSR обычно всё равно шлёт JS компонентов для гидрации; RSC держит код серверных компонентов только на сервере |

## Кратко для ответа

**CSR** — HTML почти пустой, UI строит браузер из JS; рендер только на клиенте.  
**SSR** — на каждый запрос сервер отдаёт готовый HTML + JS; клиент гидрирует.  
**SSG** — HTML заранее на build, клиенту приходит готовая статика + JS.  
**ISR** — как SSG, но HTML может обновляться позже без полного ребилда.  
Общее правило: **HTML = увидеть**, **JS = взаимодействовать**. Гидрация нужна там, где HTML уже пришёл готовым. **Hydration mismatch** — когда сервер и клиент нарисовали разное; частые причины: `Date.now()`, `Math.random()`, `localStorage`, locale/timezone, невалидный HTML. **RSC** идут дальше SSR: часть компонентов вообще не попадает в клиентский бандл.
