# Микрофронтенды

## Краткий ответ для собеседования

**Микрофронтенды** — это подход, где большой фронтенд делят на **независимые части по доменам или фичам**, и каждая часть может **разрабатываться, собираться и деплоиться отдельно**. Обычно есть **Shell / Host** — оболочка приложения, и **Remote** — подключаемые части. Часто используют **Module Federation** для загрузки модулей в рантайме. Главные плюсы: независимость команд, постепенная миграция, независимые релизы. Главные минусы: сложность интеграции, shared dependencies, согласованность UI, производительность, авторизация, маршрутизация и обмен состоянием.

---

## Что такое микрофронтенд простыми словами

Идея такая же, как у микросервисов на бэкенде: не один огромный фронтенд, а несколько более самостоятельных частей.

Пример:

- каталог товаров
- корзина
- личный кабинет
- checkout

Пользователь видит один сайт, но под капотом это могут быть **разные приложения**, за которые отвечают разные команды.

---

## Базовая схема

```text
Пользователь
   |
   v
Shell / Host
   |
   +--> Catalog Remote
   +--> Cart Remote
   +--> Profile Remote
   +--> Checkout Remote
```

### Что делает Shell

**Shell** — это приложение-оболочка.

Обычно оно отвечает за:

- общий layout: header, sidebar, footer
- верхнеуровневый роутинг
- загрузку Remote
- общие сервисы: auth, feature flags, analytics, error boundary
- общие UI-правила и дизайн-систему

Важно: хороший Shell не должен превращаться в **новый монолит**. Его задача — оркестрация, а не хранение всей бизнес-логики.

### Что такое Remote

**Remote** — отдельная часть продукта, которую можно подключить в Shell.

Обычно Remote:

- владеет своей бизнес-логикой
- имеет свой жизненный цикл разработки
- может деплоиться независимо
- отдаёт наружу страницу, виджет, модуль или целую зону интерфейса

---

## Когда микрофронтенды действительно нужны

Подход оправдан, если есть **организационная проблема**, а не просто желание "сделать модно".

Чаще всего микрофронтенды используют, когда:

- продукт очень большой
- над ним работают несколько команд
- командам нужен независимый релизный цикл
- есть естественные бизнес-домены
- идёт длительная миграция легаси

Если проект маленький, команда одна, а релизы общие, микрофронтенд чаще всего будет **избыточным усложнением**.

---

## Как делить систему

Это один из самых важных вопросов на собеседовании.

Правильнее делить не по техническим слоям, а по **бизнес-доменам**.

Хорошее деление:

- `catalog`
- `cart`
- `profile`
- `checkout`

Плохое деление:

- `buttons`
- `forms`
- `modals`
- `tables`

Почему так:

- по доменам легче назначить ответственность
- меньше пересечений между командами
- проще релизить независимо
- меньше связности между микрофронтами

На собеседовании можно сказать так:  
**микрофронтенды проектируют вокруг bounded context и пользовательских сценариев, а не вокруг маленьких UI-элементов**.

## Module Federation

**Module Federation** — самый известный механизм для микрофронтендов во фронтенде. Исторически он пришёл из Webpack 5.

Идея:

- одно приложение может **экспортировать** модуль наружу
- другое приложение может **подгрузить** этот модуль в рантайме
- общие зависимости можно шарить, а не дублировать

### Как запомнить

```text
Shell знает:
- где лежит Remote
- что у него можно взять

Remote знает:
- что он экспортирует
- как быть встроенным в Shell
```

### Что важно про Module Federation на собеседовании

- это способ **runtime composition**
- Shell не обязан собирать весь код Remote заранее
- Remote можно обновлять независимо
- есть понятие **shared dependencies**
- появляется проблема версий, контрактов и совместимости

### Плюсы Module Federation

- независимый деплой
- можно переиспользовать модули между приложениями
- удобен для постепенной миграции монолита
- можно уменьшить дублирование общих библиотек

### Минусы Module Federation

- выше сложность сборки и интеграции
- сложнее дебаг
- больше рисков с версиями зависимостей
- runtime-ошибки становятся вероятнее
- shell зависит от доступности remote

## Module Federation Enhanced (MF 2.0)

На собеседовании могут спросить не просто про Module Federation, а про **Enhanced** — современную «улучшенную» версию.

### Что это

**Module Federation Enhanced** — это развитие классического Module Federation из Webpack 5. Часто говорят как про **Module Federation 2.0**.

Коротко:

- **старая версия** — встроенный Module Federation внутри Webpack
- **Enhanced** — отдельная, более зрелая реализация с дополнительными возможностями для больших микрофронтенд-систем

Идея та же: Host загружает Remote в runtime.  
Но Enhanced делает это удобнее, стабильнее и лучше подходит для масштаба.

### Зачем он нужен

Классический Module Federation решает базовую задачу: шаринг модулей между приложениями.  
Но в больших продуктах быстро появляются боли:

- сложно дебажить
- неудобно жить с TypeScript между remote
- runtime жёстко завязан на Webpack
- не хватает удобных механизмов расширения и диагностики
- сложнее строить платформенный подход для многих команд

**Enhanced** как раз закрывает эти практические проблемы.

### Что даёт Enhanced на уровне идей

Без углубления в API, для ответа на собеседовании достаточно помнить:

- более независимый **runtime** — меньше жёсткой привязки только к Webpack
- лучше подходит для **крупных микрофронтенд-платформ**
- есть **manifest**-подход к описанию remote
- удобнее работать с **типами** между host и remote
- лучше **devtools / диагностика**
- есть **runtime plugins** — можно расширять поведение федерации
- удобнее думать про **preload**, динамическую загрузку и более взрослый DX

Главная мысль:

> Enhanced — это не «другой паттерн микрофронтендов», а более современная реализация Module Federation для реальных больших систем.

### Когда брать Enhanced

Enhanced логичен, если:

- микрофронтендов уже несколько и система растёт
- важны DX, типы, диагностика, платформенность
- хотите современный стек MF и дальше развивать архитектуру
- планируете жить с federation долго, а не как с временным экспериментом
- используете современные бандлеры / экосистему вокруг MF 2.0

Хорошая формулировка:

> Если Module Federation уже осознанно выбран как стратегия, для новых и развивающихся проектов я бы смотрел в сторону Enhanced.

### Когда лучше пока оставить старую версию

Старый / встроенный Module Federation ещё нормален, если:

- уже есть рабочая стабильная система на классическом MF
- команда не готова к миграции прямо сейчас
- нет боли в типах, дебаге и платформенных штуках
- продукт небольшой, federation используется точечно
- риск миграции выше, чем ожидаемая польза

То есть:

- **старый MF** — ок для legacy и «уже работает, не ломай»
- **Enhanced** — лучше для нового витка развития и масштаба

### Важный нюанс совместимости

На собеседовании полезно сказать аккуратно:

- Enhanced обычно позиционируют как путь вперёд
- миграция часто относительно прямая по идее
- но в сложных системах с кастомными хаками совместимость host/remote разных поколений нужно проверять
- поэтому большие платформы мигрируют **постепенно**, а не «всё и сразу»

### Как запомнить разницу

```text
Классический Module Federation
  → базовая runtime-загрузка модулей
  → появился с Webpack 5
  → достаточно для старта

Enhanced / MF 2.0
  → та же идея
  → но удобнее для больших MFE
  → лучше DX, типы, диагностика, расширяемость
```

### Что сказать на собеседовании за 20 секунд

> Классический Module Federation решает базовую задачу шаринга модулей между host и remote. Enhanced — это его современная версия для более зрелых микрофронтенд-систем: лучше DX, типизация, диагностика и расширяемость runtime. Для нового или растущего проекта я бы выбирал Enhanced, а старую версию оставлял в legacy, если система уже стабильно работает и миграция пока не окупается.

## Shared Dependencies

Это одна из самых важных тем.

**Shared dependencies** — библиотеки, которые несколько микрофронтов используют совместно:

- React
- React DOM
- router
- дизайн-система
- i18n
- ui-kit

### Зачем их шарить

Если каждый микрофронт загрузит свою копию React и UI-библиотеки, будут проблемы:

- лишний вес JS
- дублирование кода
- риск конфликтов между версиями
- возможные баги, если библиотека должна быть singleton

### Что обычно шарят

Чаще всего шарят:

- framework runtime
- router
- design system
- библиотеки состояния, если это оправдано
- общие утилиты и типы, но не всё подряд

### Плюсы shared dependencies

- меньше дублирования
- ниже размер загружаемого кода
- единое поведение ключевых библиотек
- проще поддерживать одну дизайн-систему

### Проблемы shared dependencies

- жёсткая зависимость от совместимых версий
- апдейт одной библиотеки может затронуть несколько команд
- может возникнуть "скрытая связанность"
- если shared-библиотека сломалась, падает сразу несколько частей

### Главная мысль

**Шарить нужно только то, что действительно должно быть общим.**  
Если шарить слишком много, микрофронтенды теряют независимость и превращаются в распределённый монолит.

---

## Singleton зависимости

На собеседовании любят спрашивать, почему React часто делают singleton.

Смысл:

- должен быть один общий runtime
- иначе можно получить проблемы с контекстами, хуками, рендерингом и несовместимостью

Обычно singleton-ами делают:

- React
- React DOM
- иногда router и state runtime

Но даже здесь нужен аккуратный контроль версий.

## Shell: плюсы и минусы

### Плюсы Shell

- единая точка входа
- единая навигация
- удобно централизовать auth, analytics, feature flags
- можно контролировать UX и общую композицию
- проще встроить общие fallback-сценарии

### Минусы Shell

- риск, что он станет "бог-объектом"
- если Shell нестабилен, страдает всё приложение
- он может стать bottleneck для команд
- туда часто начинают складывать лишнюю бизнес-логику

### Хороший Shell

Хороший Shell:

- тонкий
- отвечает за orchestration, а не за доменную логику
- задаёт контракты
- обеспечивает общие сервисы
- не знает внутренности каждого Remote

### Плохой Shell

Плохой Shell:

- содержит половину продукта
- управляет всеми состояниями напрямую
- зависит от деталей каждого Remote
- требует частых изменений при любом релизе

## Как микрофронтенды общаются

Это один из самых частых вопросов на собеседовании по микрофронтендам.

**Главный принцип:** микрофронтенды должны быть слабо связаны и общаться через **явные, стабильные контракты**, а не через прямые зависимости.

---

### Способ 1: URL и навигация

Самый предпочтительный и самый недооценённый способ.

**Как работает:**

- Один Remote меняет URL (или query-параметры)
- Shell или другой Remote читает URL и реагирует

**Примеры:**

- перейти на другую страницу
- передать ID сущности через route
- сохранить фильтры в query string

**Плюсы:**

- никакой прямой зависимости между микрофронтами
- всегда можно восстановить состояние по URL
- стандартный механизм браузера

**Минусы:**

- не подходит для реактивных UI-событий внутри страницы
- в URL не засунешь сложные объекты

---

### Способ 2: Custom Events (браузерные события)

Один Remote отправляет событие в `window`, другой его слушает.

**Как работает:**

```text
Catalog Remote --[CustomEvent: item-added]--> window
Cart Remote слушает window и реагирует
```

**Плюсы:**

- нет прямой зависимости между Remote
- стандартный браузерный механизм
- прост в реализации

**Минусы:**

- нет типизации из коробки
- легко получить "магические строки" с названиями событий
- нет гарантии доставки
- сложнее дебажить

**На собеседовании:** нужно добавить, что обычно создают **реестр событий** с договорёнными названиями, чтобы не было хаоса.

---

### Способ 3: Event Bus (pub/sub шина)

Более структурированный вариант событий. Общая шина сообщений, которую можно шарить как shared dependency.

**Как работает:**

```text
Catalog Remote  -->  EventBus.emit('cart:item-added', payload)
Cart Remote     <--  EventBus.on('cart:item-added', handler)
```

**Схема:**

```text
Catalog Remote
   | emit('cart:item-added')
   v
EventBus (shared)
   |
   v
Cart Remote
   | слушает 'cart:item-added'
```

**Плюсы:**

- более структурировано, чем raw Custom Events
- можно типизировать
- можно логировать события централизованно

**Минусы:**

- шина становится неявной зависимостью
- нужно договариваться о контракте событий
- при плохом дизайне превращается в глобальный event soup

---

### Способ 4: Shell API (Props / Context через Shell)

Shell передаёт Remote нужные данные или функции при монтировании.

**Как работает:**

```text
Shell
  | передаёт props: { user, onLogout, onNavigate }
  v
Remote
```

**Плюсы:**

- явный контракт
- Remote ничего не "тянет" сам
- удобно для cross-cutting данных (user, permissions, theme)

**Минусы:**

- Shell должен знать, что нужно каждому Remote
- риск, что Shell начнёт управлять всем

---

### Способ 5: Shared State (общий store)

Несколько Remote читают и пишут в единый слой состояния.

**Как работает:**

```text
Catalog Remote --> SharedStore.dispatch(addItem)
Cart Remote    <-- SharedStore.select(cartItems)
```

**Плюсы:**

- удобно, если данные реально нужны в нескольких местах
- привычно для разработчиков, знакомых с Redux

**Минусы:**

- сильная зависимость между Remote
- релизы становятся связанными
- изменение структуры store влияет на всех
- риск распределённого монолита

**Когда допустимо:** только для действительно cross-cutting state: auth, user, feature flags, тема — не для доменных данных.

---

### Способ 6: Backend / BFF как источник истины

Если оба Remote нуждаются в одних и тех же данных, иногда лучший ответ — просто **запросить у сервера заново**.

**Как работает:**

```text
Catalog Remote --> добавил в корзину --> вызвал BFF
Cart Remote    --> перерендерился     --> запросил актуальные данные у BFF
```

**Плюсы:**

- нет прямой связи между Remote
- источник истины всегда на сервере
- легче тестировать

**Минусы:**

- дополнительный сетевой запрос
- нужна хорошая работа с кешем на клиенте

**На собеседовании:** это часто недооценённый, но очень правильный ответ. Не каждую синхронизацию нужно решать клиентским state.

---

### Сводная таблица способов

| Способ | Когда использовать | Слабые стороны |
|--------|-------------------|----------------|
| URL / навигация | переходы, передача ID, фильтры | не для UI-событий внутри страницы |
| Custom Events | редкие сигналы, нет общего state | нет типизации, магические строки |
| Event Bus | структурированные события | риск event soup, неявная зависимость |
| Shell API / Props | cross-cutting данные от Shell | Shell может знать слишком много |
| Shared Store | auth, user, theme, feature flags | связывает Remote, риск монолита |
| Backend / BFF | данные, которые нужны нескольким Remote | сетевой запрос, нужен кеш |

---

### Приоритет способов (как отвечать на собеседовании)

```text
1. URL и навигация            — самый чистый вариант
2. Backend / BFF              — для общих данных
3. Shell API / Props          — для cross-cutting concerns
4. Custom Events / Event Bus  — для слабосвязанных сигналов
5. Shared Store               — только если нельзя иначе
```

### Что опасно

- прямые `import` из кода другого Remote
- общий Redux-store для доменных данных
- синхронные вызовы функций из соседнего Remote
- слишком много событий без реестра и типизации

### Главный сигнал для собеседования

Если два микрофронта постоянно и тесно общаются, это сигнал, что **их, возможно, не стоило разделять**.

---

## Состояние в микрофронтендах

Главный принцип:

**не нужно делать одно глобальное состояние на всё приложение по умолчанию**.

Лучше:

- локальное состояние держать внутри Remote
- общие вещи хранить в Shell только если это действительно cross-cutting concern

Что часто бывает общим:

- авторизация
- информация о пользователе
- feature flags
- тема
- locale

Что лучше не делать общим без необходимости:

- локальные формы
- состояние конкретной страницы
- временное UI-состояние доменной зоны

### Redux в микрофронтендах

Если в проекте используют **Redux**, то главное правило такое:

**Redux-store не должен автоматически становиться "общим мешком для всего приложения".**

Лучший подход:

- у каждого Remote может быть **свой локальный store**, если его состояние относится только к его домену
- в Shell должен жить только **глобальный кросс-доменный state**
- общий Redux нужен только там, где действительно есть общие сценарии

### Где должен жить state

#### 1. State внутри Remote

Сюда обычно относится:

- состояние каталога
- локальные фильтры страницы
- состояние checkout-шага
- локальные формы
- UI-состояние конкретной доменной зоны

То есть всё, чем владеет один bounded context, лучше держать **внутри своего микрофронта**.

#### 2. State в Shell

В Shell обычно имеет смысл хранить только то, что нужно сразу нескольким Remote:

- auth/session
- текущий пользователь
- feature flags
- locale
- тема
- глобальные permissions
- иногда состояние верхнеуровневой навигации

Это не доменный state, а **platform state**.

### Когда нужен общий Redux-store

Общий store допустим, если:

- несколько микрофронтов действительно читают одни и те же данные
- без синхронизации будет сильное дублирование
- это кросс-продуктовая сущность, а не локальная логика одной команды

Но даже тогда лучше, чтобы общий store был:

- небольшим
- ограниченным по ответственности
- стабильным по контракту

### Когда общий Redux-store опасен

- если туда складывают state всех доменов
- если один Remote может свободно менять state другого
- если релизы начинают зависеть от структуры общего store
- если все команды вынуждены синхронно обновлять селекторы, reducers и actions

Это прямой путь к **распределённому монолиту**.

### Практичное правило для собеседования

Можно отвечать так:

**локальный доменный state держим внутри Remote, а в Shell выносим только cross-cutting state: auth, user, feature flags, theme, locale. Один глобальный Redux на всё приложение делаем только при реальной необходимости, иначе микрофронты теряют независимость.**

### Если очень нужен общий state

Тогда лучше, чтобы микрофронты работали не с "чужими" внутренностями, а с:

- публичным shell API
- ограниченным shared store
- событиями
- backend/BFF как источником истины

То есть важна не просто "общая память", а **контролируемый контракт**.

### Что часто лучше Redux

Во многих случаях между микрофронтами лучше работают:

- URL как источник состояния навигации
- повторный запрос к backend/BFF
- события для редких сигналов
- локальный state внутри домена

Если данные нужны нескольким Remote, это ещё не значит, что их обязательно надо класть в один Redux-store.

---

## Авторизация и безопасность

С микрофронтендами auth становится сложнее, потому что пользователь ожидает **единый вход**, а система внутри разбита.

Обычно нужно продумать:

- единый механизм аутентификации
- кто хранит токен
- как обновлять токен
- кто отвечает за logout
- как защищать routes и remote

На собеседовании важно отметить:

- микрофронтенд не отменяет общую security-модель
- нельзя, чтобы каждый remote придумывал auth по-своему
- auth и permissions обычно централизуют

---

## Как микрофронтенды взаимодействуют с BFF

Очень хороший ответ на собеседовании:

**микрофронты не должны компенсировать отсутствие нормального backend-контракта общим Redux-store и хаотичными запросами. Часто правильнее дать им BFF, который отдаёт данные в форме, удобной для конкретного экрана или домена.**

### Базовая схема

```text
Пользователь
   |
   v
Shell / Remote
   |
   v
BFF
   |
   +--> Users Service
   +--> Orders Service
   +--> Catalog Service
   +--> Payments Service
```

### Как лучше строить взаимодействие

- микрофронт обращается не к десятку микросервисов, а к своему API-слою
- этот слой часто смотрит в сторону **BFF**
- BFF агрегирует данные из внутренних сервисов и отдаёт ответ в формате, удобном фронту

### Что это решает

- меньше сетевых запросов с клиента
- меньше knowledge о внутреннем устройстве бэкенда
- меньше склейки данных на фронте
- проще типизация и обработка loading/error
- проще менять внутренние сервисы без переписывания фронта

### Как делить BFF относительно микрофронтов

Есть несколько рабочих вариантов:

#### 1. Один общий BFF для всего продукта

Подходит, если:

- продукт ещё не очень большой
- команды тесно связаны
- нужен единый серверный слой

Риск:

- BFF сам становится монолитом

#### 2. BFF по доменам

Например:

- catalog BFF
- cart BFF
- profile BFF

Плюсы:

- ближе к границам микрофронтов
- командам проще владеть своим контрактом

Риски:

- больше инфраструктурной сложности
- нужен общий подход к auth, observability и ошибкам

#### 3. Общий platform BFF + доменные BFF

Частый компромисс:

- platform BFF решает auth, session, общие метаданные
- доменные BFF отдают данные для своих зон

### Где должен быть источник истины

Если данные важны для нескольких микрофронтов, часто лучший источник истины — не общий Redux-store, а:

- **backend/BFF**
- а на фронте только кеш и локальное представление

То есть:

- данные живут на сервере
- микрофронты их запрашивают через стабильный API
- Redux не должен заменять backend

### Что важно не делать

- не давать каждому микрофронту напрямую знать про все внутренние микросервисы
- не переносить серверную агрегацию данных в Shell
- не использовать глобальный Redux как substitute для BFF

На собеседовании это звучит сильно:  
**BFF отвечает за агрегацию и адаптацию данных, а Redux — за клиентское состояние. Нельзя пытаться решать серверные проблемы клиентским store.**

---

## UI-consistency

Одна из главных проблем микрофронтендов — пользователь не должен заметить, что продукт "сшит" из частей.

Что помогает:

- единая дизайн-система
- общие токены дизайна
- единые правила навигации
- общие паттерны ошибок, загрузок, пустых состояний
- общая терминология

Если этого нет, продукт начинает выглядеть как набор разных сайтов.

---

## Производительность

Микрофронтенды часто проигрывают монолиту по производительности, если их спроектировать неаккуратно.

Основные риски:

- несколько runtime и библиотек
- лишние сетевые запросы
- повторная инициализация зависимостей
- тяжёлый shell
- медленная загрузка remote

### Как мыслить на собеседовании

Нужно сказать, что независимость команд покупается ценой runtime-overhead.

То есть вопрос не "микрофронтенд быстрее или медленнее", а:

- какие части грузить лениво
- что шарить
- как держать Shell тонким
- как кешировать remote
- как строить graceful fallback

---

## Плюсы микрофронтендов

- независимые команды
- независимые релизы
- понятное разделение по доменам
- проще мигрировать по частям
- можно изолировать ответственность
- можно постепенно выделять legacy-зоны

---

## Минусы микрофронтендов

- высокая архитектурная сложность
- сложнее тестирование и дебаг
- сложнее авторизация и маршрутизация
- сложнее observability и мониторинг
- риск дублирования зависимостей
- риск рассинхронизации UI/UX
- риск превращения в распределённый монолит

---

## Что такое распределённый монолит

Это очень полезный термин для собеседования.

**Распределённый монолит** — это когда систему формально разбили на части, но на практике они так сильно зависят друг от друга, что независимо жить не могут.

Признаки:

- общий релизный цикл
- постоянные координации между командами
- жёсткие зависимости по версиям
- общий store без границ
- один микрофронт не работает без другого

То есть внешне это микрофронтенды, а по факту всё ещё монолит, только сложнее.

---

## Как проектировать микрофронтенды

### 1. Начинать с организационной причины

Сначала нужно понять:

- какие команды есть
- где границы ответственности
- какие части хотят релизиться независимо

### 2. Делить по доменам

Границы должны быть близки к бизнесу, а не к техническим слоям.

### 3. Держать контракты простыми

Remote должен иметь понятный и стабильный контракт:

- что он экспортирует
- какие входные данные принимает
- что обещает наружу

### 4. Минимизировать shared

Общими делать только действительно важные зависимости и сервисы.

### 5. Централизовать cross-cutting concerns

Обычно в Shell или общей платформе живут:

- auth
- analytics
- feature flags
- error handling
- дизайн-система
- базовые инфраструктурные сервисы

### 6. Продумывать деградацию

Если один Remote не загрузился, приложение не должно превращаться в белый экран.

Нужны:

- fallback UI
- retry
- error boundaries
- мониторинг

### 7. Не путать свободу с хаосом

Технологическая свобода не значит, что каждая команда должна брать случайный стек.

Часто разумнее договориться:

- об одной дизайн-системе
- об общих правилах observability
- о подходе к routing
- о принципах versioning

---

## Простая схема принятия решения

```text
Одна команда + общий релиз?
   -> скорее монолит или модульный монолит

Много команд + разные домены + независимые релизы?
   -> возможно микрофронтенды

Нужна только модульность без отдельного деплоя?
   -> модульный монолит
```

## Микрофронтенды и Next.js

### Может ли часть микрофронтов быть на Next.js, а часть — React SPA?

**Да, может.** Это реальный сценарий, и на собеседовании о нём спрашивают.

Каждый микрофронт — **отдельное приложение**, и технически ничто не мешает использовать в одном домене `Next.js`, а в другом — обычный React SPA. Пользователь это не заметит, если интеграция сделана правильно.

### Когда это имеет смысл

Типичные причины смешивать Next.js и SPA:

- часть продукта требует **SEO** (например, публичный каталог) — туда ставят Next.js
- часть приложения полностью **авторизованная** и SEO не нужен — там достаточно SPA
- **постепенная миграция**: был один SPA-монолит, новые домены делают на Next.js
- разные команды с разными предпочтениями и обоснованным выбором стека

### Пример разбивки

```text
Shell (Next.js)
   |
   +--> Catalog Remote (Next.js — нужен SSR для SEO)
   +--> Cart Remote (React SPA — авторизованная зона, SEO не нужен)
   +--> Profile Remote (React SPA — личный кабинет)
   +--> Checkout Remote (Next.js — критичен time-to-first-paint)
```

---

### Как Next.js и Module Federation уживаются вместе

Next.js исторически плохо дружил с Module Federation, потому что у него своя сборочная система. Но ситуация улучшилась.

#### Что нужно знать

- для Next.js 13+ / App Router есть плагин `@module-federation/nextjs-mf`
- он добавляет поддержку Module Federation поверх Next.js webpack-конфига
- работает, но со своими ограничениями

#### Ограничения

- `SSR` с Module Federation сложнее, чем с чистым CSR: нужно, чтобы Remote умел рендериться и на сервере
- если Remote — чистый React SPA, его нельзя использовать в SSR-части Shell напрямую, только на клиенте
- нужно аккуратно разграничивать, какие части рендерятся на сервере, а какие — только в браузере

---

### Три реальных сценария

#### Сценарий 1: Shell на Next.js, Remote — React SPA

```text
Shell (Next.js, SSR)
   |
   +--> Cart Remote (React SPA)
        ^ подключается только на клиенте
```

**Как работает:**

- Shell рендерится на сервере и отдаёт HTML
- Remote-модули подгружаются только после гидратации в браузере
- для пользователя: быстрый первый экран от Shell, затем Remote догружается

**Что важно:**

- Remote нельзя использовать в серверных компонентах Shell
- нужен `dynamic import` с `ssr: false`
- на стороне Shell нужен fallback на время загрузки Remote

**Плюсы:**

- Shell получает преимущества SSR
- Remote-команды могут работать без Next.js

**Минусы:**

- Remote не участвует в SSR
- возможен layout shift или мигание при загрузке

---

#### Сценарий 2: Shell — React SPA, Remote — Next.js

Встречается реже, потому что обычно SEO важен для публичных страниц, а не для авторизованных зон.

Но технически возможно: Remote на Next.js работает как самостоятельный сервер и отдаёт страницу через `iframe` или как отдельный маршрут.

---

#### Сценарий 3: Shell на Next.js, Remote тоже на Next.js

Самый сложный вариант.

**Проблема:**

- два Next.js приложения — это два независимых сервера
- один не может нативно рендерить серверные компоненты другого
- Router, Auth, Cache — у каждого свои

**Как обычно решают:**

- Remote экспортирует **только клиентские компоненты** (с `'use client'`)
- Shell подгружает их через Module Federation уже в браузере
- SSR Remote не смешивается с SSR Shell

```text
Shell Next.js (SSR)
   |
   +--> [server render Shell pages]
   |
   +--> [client hydration]
         |
         +--> Remote Next.js (только client components)
```

**На собеседовании важно сказать:**

SSR двух независимых Next.js приложений нельзя нативно объединить — рендер происходит на разных серверах. Поэтому микрофронты на Next.js обычно шарят только **клиентские компоненты**, а не серверные.

---

### Роутинг при смешанном стеке

Это отдельная боль.

**Проблема:** у каждого приложения свой роутер.

- Next.js Router
- React Router
- `window.history` напрямую

**Как обычно решают:**

- Shell владеет верхнеуровневым роутингом
- Remote отдаёт только страницу или компонент, без своего роутера на верхнем уровне
- при навигации Shell решает, какой Remote монтировать
- Remote может иметь внутренний роутинг **внутри своей зоны**

```text
Shell (Router верхнего уровня)
   /catalog/*  --> Catalog Remote (может иметь свой Router внутри)
   /cart/*     --> Cart Remote
   /profile/*  --> Profile Remote
```

---

### Auth при смешанном стеке

Next.js часто управляет auth на уровне middleware или серверных компонентов. Если Remote — SPA, у него нет этого слоя.

**Обычный подход:**

- auth централизован в Shell или в отдельном сервисе
- Remote получает токен/сессию через Shell API
- Next.js middleware для защиты маршрутов — только в том приложении, где он стоит

---

### Плюсы смешанного Next.js + SPA подхода

- можно применять SSR только там, где он нужен
- команды работают с привычным стеком
- постепенная миграция с SPA на Next.js по доменам
- SEO только для публичных зон, SPA — для авторизованных

### Минусы смешанного подхода

- сложнее общая инфраструктура
- нет единого подхода к роутингу, auth, кешированию
- Module Federation с Next.js требует дополнительной настройки
- серверный рендер Remote в SSR Shell — нетривиальная задача
- потенциально разные подходы к data fetching

---

### Альтернатива Module Federation: Sub-path деплой

Иногда вместо Module Federation микрофронты просто **деплоятся на разные пути**:

```text
example.com/          -> Shell (Next.js)
example.com/catalog/  -> Catalog Remote (Next.js, отдельный сервер)
example.com/profile/  -> Profile Remote (React SPA)
```

Переключение происходит на уровне `nginx` или CDN — каждый путь проксируется на свой сервер/бакет.

**Плюсы:**

- полная независимость приложений
- нет общего Module Federation и сложной конфигурации Webpack
- любой стек, любой сервер

**Минусы:**

- полная перезагрузка страницы при переходе между доменами (если не настроен SPA-like переход)
- сложнее поддерживать единый layout без дублирования
- auth и state не шарятся автоматически

Это не всегда "плохой" вариант — иногда это **самый честный микрофронтенд**: приложения действительно независимые.

---

### Что говорить на собеседовании

Когда спрашивают про Next.js + микрофронтенды:

1. Смешивать Next.js и React SPA **можно и это реальный сценарий**
2. Module Federation поддерживает Next.js через `@module-federation/nextjs-mf`, но с ограничениями
3. SSR двух разных Next.js приложений **нельзя нативно объединить** — шарят только клиентские компоненты
4. Remote на React SPA в SSR-Shell работает только на клиенте — нужен `dynamic import` с `ssr: false`
5. Роутинг централизуют в Shell, каждый Remote управляет только своим внутренним роутингом
6. Альтернатива Module Federation — **sub-path деплой** через nginx/CDN, но тогда нет SPA-навигации

## Частые вопросы на собеседовании

| Вопрос | Краткий ответ |
|--------|----------------|
| Что такое микрофронтенд? | Архитектура, где фронтенд делят на независимые части с отдельной сборкой и деплоем, но пользователь видит одно приложение. |
| Что такое Shell? | Оболочка приложения: роутинг, layout, загрузка remote, общие сервисы. |
| Что такое Remote? | Независимая часть системы, которую Shell подключает и отображает. |
| Что такое Module Federation? | Механизм runtime-загрузки модулей из других приложений, часто используемый для микрофронтендов. |
| Что такое Module Federation Enhanced? | Современная версия MF (часто MF 2.0) с лучшим DX, типами, диагностикой и расширяемым runtime для крупных MFE. |
| Когда брать Enhanced, а когда старый MF? | Enhanced — для новых/растущих систем; старый MF — если legacy уже стабилен и миграция пока не нужна. |
| Что такое shared dependencies? | Общие библиотеки, которые несколько микрофронтов используют совместно, чтобы не дублировать runtime и поведение. |
| Почему shared dependencies могут быть проблемой? | Из-за версий, связности, скрытых зависимостей и риска ломать сразу несколько частей. |
| Почему Shell опасен? | Он может стать новым монолитом и bottleneck, если туда унести бизнес-логику. |
| Как делить микрофронтенды? | По доменам и bounded context, а не по мелким UI-элементам. |
| Когда не стоит брать микрофронтенды? | Когда проект небольшой, команда одна, релизы общие и нет проблемы организационного масштаба. |
| Что такое распределённый монолит? | Формально части разделены, но на практике они сильно зависят друг от друга и не живут независимо. |
| Можно ли смешивать Next.js и React SPA в микрофронтендах? | Да. Часть Remote может быть на Next.js (где нужен SSR/SEO), часть — React SPA (авторизованные зоны). |
| Можно ли рендерить Remote на сервере в SSR Shell? | Только если Remote тоже Next.js и экспортирует клиентские компоненты. Два разных SSR-сервера нельзя объединить нативно. |
| Как подключить React SPA Remote в Next.js Shell? | Через dynamic import с ssr: false — Remote загружается только на клиенте после гидратации. |

---

## Кратко запомнить

**Микрофронтенды** — это не просто техника загрузки модулей, а способ масштабировать фронтенд **организационно и архитектурно**. Основа — **Shell + Remote**, частый инструмент — **Module Federation**, для зрелых систем — **Enhanced / MF 2.0**. Сложное место — **shared dependencies** и границы между доменами. Главный риск: вместо гибкости получить **распределённый монолит**.
